# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Fuel station management app (gasoil/essence) for a station in Goma, DRC: amounts in US dollars, timezone `Africa/Lubumbashi`. All UI text, server error messages and the README are in **French**; keep it that way. `README.md` documents the business rules (reconciliation formula, customer categories, combos) and is the reference when behavior is in doubt.

## Commands

- `npm start`: serve on `PORT` (3000), with the database at `DB_FILE` (default `data/station.db`).
- `npm run dev`: same, with `--watch`.
- `npm test`: `node:test` API tests.
- Single test: `npm test -- --test-name-pattern="combos"`. The tests in `test/api.test.js` share **one** in-memory app created in `before()` and depend on each other's state (setup → shift → sales…), so a filtered run can fail where the full run passes.

Requires Node ≥ 22.13 (built-in `node:sqlite`, hence `--disable-warning=ExperimentalWarning` in every script). The only dependency is Express 5. There is no build step, no bundler and no linter.

## Architecture

**Server** (`src/`, CommonJS):
- `createApp({ dbFile })` in `src/app.js` mounts each `src/routes/*.js` factory `(db) => Router` under `/api`.
- Errors are thrown, never returned: use `fail(status, message, code)` / `HttpError` from `src/util.js`. The error handler replies `{ error, code }`, and the frontend branches on `code` (e.g. `over_limit` opens a "grant credit?" confirmation, `duplicate`, `combos`).
- Input validation uses the `num`, `str`, `oneOf`, `bool`, `dateParam` helpers. Multi-step writes go in `transaction(db, fn)` (BEGIN IMMEDIATE).
- Auth (`src/auth.js`): cookie `sid` (sha256-hashed session token), scrypt passwords, `requireRole('manager' | 'attendant' | 'customer')`. A customer user is linked through `users.customer_id`. The owner (`owner`, « Actionnaire », version 15) reads everything and changes nothing: `loadUser` passes them as a manager on GET/HEAD (`req.user.owner` stays true) and any other request keeps role `owner`, refused with `code: 'read_only'` (exceptions: `/auth/password`, the meters preview). The admin (`admin`, version 17: the account created at setup, and the first manager on migration) is a manager who alone changes the settings, the team and the cash book: `loadUser` passes them as a manager with `req.user.admin`, `requireAdmin` guards those routes (`code: 'admin_only'`), `/auth/me` returns `admin: true`, and the client wraps those controls in `adminEdit()` / `canAdmin()` (`flags.admin`). The owner has no settings nor journal (`NAV.owner`). The manager sees Réglages with no button at all (no price history, no backup, no journal: `canAdmin()`). A customer created at the pump gets their client space from « Créer un accès » on their record (`POST /customers/:id/login`): login = their phone, default password 12345678 (`DEFAULT_PASSWORD` in `customers.js`), then `shareAccess()` sends the link, login and password through the phone's native share sheet (`navigator.share`, a copy otherwise); the customer changes the password from their account menu. The client sets `flags.readonly` and wraps every write control in `edit()` from `ui.js`; a new manager button that writes must be wrapped too.

**Database** (`src/db.js`):
- One `SCHEMA` string of `CREATE TABLE IF NOT EXISTS`.
- Schema changes on existing databases:
  - new columns go into `MIGRATIONS` (`[table, column, definition]`, added when missing, in one transaction) and bump `SCHEMA_VERSION` (`PRAGMA user_version`);
  - a database holding data is copied to `<db>.avant-migration-…` before any change;
  - a CHECK constraint change needs a table rebuild, like `migrateSalesKind` / `migrateRequests`.
  - Production data on Render must survive, so add a migration and a migration test.
- Settings are key/value rows. `getSettings(db)` maps them to camelCase (`combosPerLiter`, `comboValue`, `comboThreshold`, `subscriberGraceDays`, `stationPhone` shown at the bottom of the client space, …). `subscriberGraceDays` is only the default payment day of a new subscriber: each subscriber has `customers.payment_day` (version 21, null for a particulier), read by `subscriberDues()`.
- There is no credit limit any more (version 19): `customers.credit_limit` and the `*_credit_limit` settings are left over, unused and not editable. An individual has one credit at a time (`has_credit`; `GET /customers/:id/unpaid` lists what is owed, shown by `creditBlocked()` in `attendant.js` as a centred `noticeDialog`), a subscriber pays each month.
- Dashboard alerts carry a `type` and a stable `key`; `userAlerts()` (`src/alerts.js`) filters them per user (`alert_prefs`: types switched off, `alert_hidden`: one alert hidden while its text is the same) and `PUT /alerts` saves the choices (« Gérer » on the Alertes card, also for the owner). A new alert needs a type in `ALERT_TYPES`.
- Naming: customer `type` is `'account'` = abonné (subscriber) and `'individual'` = particulier.
- Customer names are unique, compared by `nameKey()` (case, accents, spaces) in `src/routes/customers.js` (`checkName()`, `customerNamed()` also used by `/register`; `code: 'duplicate'`); no index, older namesakes are only flagged « Même nom » in the list. « Supprimer » on a record: `DELETE /customers/:id` when it has no operation (`OPERATIONS`: sales, payments, old_debts, purchase_requests) nor login (`has_operations` otherwise), else `POST /customers/:id/merge { into }` moves them, the mail log and the login to the other customer, fills its empty contact fields, deletes the record, `refreshCustomer()`, journalled. A new table with `customer_id` must be added to `OPERATIONS` or to the merge.

**Core business logic** (shared by several routes):
- `src/sales.js` `createSale(db, shift, input)`: the only way a sale is created. It is used both by the attendant's sale form and by the confirmation of a customer purchase request (`afterInsert` marks the request confirmed in the same transaction). It handles:
  - subscriber price;
  - $ ↔ litres conversion at the shift's frozen price;
  - payment `paid` | `credit` | `combo`;
  - one credit at a time for an individual (`has_credit`, never overridden) and the late-subscriber check (`grantCredit` overrides it and sets `over_limit`, shown « crédit malgré le retard »).
- `src/loyalty.js`:
  - payments settle credit sales FIFO (`creditAllocation`);
  - a credit sale's combos (`points_due`) only become `points` once fully paid;
  - `refreshCustomer` recomputes this and `customers.loyalty_points`, so call it after any change to a customer's sales or payments;
  - `subscriberDues` computes what a subscriber owes for previous months.
- Shifts (`src/routes/shifts.js`):
  - one shift, always open, for the whole station and every active pump: `POST /shifts` only opens the very first one; the manager's 15:30 closing (`POST /shifts/:id/close`, manager only) opens the next at once (`openShift()`), carrying the attendants on duty. `closing_time` (setting) drives the reminder (`closingCutoff()` in `src/checkpoints.js`);
  - attendants are in `shift_attendants` (several at once; `left_at` on relief or evening closing). To enter anything an attendant must be on duty (`not_on_duty`) and the station open (`station_closed`); `GET /shifts/state` drives the attendant's screen;
  - the manager's « État du poste » (`#/postes/:id/etat`, `public/js/views/shiftStatus.js`; the router passes a third hash segment as `ctx.sub`) reads the shift detail and checks the meters through `POST /shifts/:id/checkpoints/preview`, which saves nothing;
  - checkpoints (`shift_checkpoints` + `checkpoint_readings`): `releve` (relief, money passed to the next), `fermeture` (19:00, sets `station_closed_at`, the shift stays open), `ouverture` (6:30). `src/checkpoints.js` builds each checkpoint's report always from the shift's opening (its start indexes, the change it received, every operation since: litres, sales, credits, money expected vs the money in the till then), never from the previous checkpoint; the manager's « État du poste » and its meter preview count from the opening too; a relief's report reaches every other attendant, even on duty: `GET /shifts/reports/unseen` (polled with the requests on the attendant's screen) lists the reliefs by others they have not seen (`checkpoint_seen`, version 20; taking the shift marks the earlier ones seen), shown in a centred `noticeDialog` with `reportCard`, then `POST /shifts/reports/:id/seen`;
  - opening snapshots meter indexes and prices into `shift_readings` (prices are frozen for the shift);
  - closing reconciles litres from the indexes against cash: `expected = sold + subscriber surcharge − credit − combos + payments collected − cash expenses ± cash book movements made in the till` (a cash entry or exit, or a mobile money withdrawal into the cash (`retrait_momo`, +), recorded with « Dans l’argent du poste en cours » (`shiftSign()` in `src/cashbook.js`), gets `cash_movements.shift_id`, version 24; `shiftMovements()` in `src/checkpoints.js` is read by `reconcile()`, the checkpoint reports, the closing form, the shift PDF; the cash book shows it at its time and takes it off the shift's closing line; it cannot be removed once its shift is closed; a movement entered without it is put in, or taken out of, the money of the shift open at its time by touching it in the cash book: `POST /cashbook/movements/:id/shift`, which reconciles a closed shift again through `mailer.services.reconcile`).
  - not every sale is entered: the shift's sales come from the indexes, and entered sales only record credits, combos and subscriber prices;
  - `GET /shifts/:id/report.pdf` (closed shifts) is the end-of-shift report: cash, sales from the indexes, credits, expenses, payments. It is built by `src/shiftReport.js` on `src/pdf.js`, a dependency-free PDF writer (Helvetica, WinAnsi). The shift page and Rapports offer it with a single « Partager » button (`shareButton()` in `ui.js`: the share sheet, or a download where files cannot be shared).
- Closing logic is `applyClosing()` in `src/routes/shifts.js`, used by `POST /shifts/:id/close` (the attendant, or the manager in their place) and `POST /shifts/:id/correct` (manager: undoes meters and tank stock, closes again, reason required). Operations entered wrongly: `PUT /shifts/:id/:kind/:itemId` (manager; `updateSale()` in `src/sales.js` for credits, no credit rule checked again) corrects a credit, payment, mobile money entry or expense, open or closed shift (reconciled), journalled before/after; in the UI the manager touches the row (`shiftSummary(…, onEdit)`). Forgotten operations (API only, no screen since « Corriger la clôture » went back to indexes and money): `getOwnShift(req, { late: true })` lets the manager add a credit, payment, mobile money entry, expense or pump test to a closed shift; `lateEntry()` reconciles it again and journals it (pump tests go through `applyTests()`). The closing has two steps: `/close` may come with the end meters only (the next shift opens at once; `counted_at` stays null, `variance` null, a dashboard alert « argent à compter »), then `POST /shifts/:id/count` (cash, change left, once; passes the change to the next shift); a closing with cash counts at once, and a correction of a counted shift needs the cash again. The manager's closing is final: there is no validation step (old `validated` shifts became `closed` in version 11). The cash count is in dollars and only the cash is typed: mobile money is entered as it is paid (`POST /shifts/:id/momo`, table `momo_sales`: litres of one product at the shift's price), and `momoTotal()` (`src/checkpoints.js`, these entries + payments by mobile money) gives `shifts.mobile_money`, recomputed by `reconcile()`. Checkpoints count the cash only: mobile money stays on the station's account, it is not passed on. At the closing the manager may leave change with the attendants (`shifts.change_left`) and types the cash handed over (`cash`, without that change, since version 14): cash to hand over = expected − mobile money − change left, and the variance counts cash + change + mobile money. The next shift receives it (`change_received`, added to its expected amount and to its first period's `received`); the cash book gets `cash`. The closing also snapshots each tank (`shift_tank_stock`: litres sold, stock left) for the shift report. No card, no bank, no francs congolais (`shifts.card` only holds old data).
- Pump tests (`pump_tests`): fuel drawn at the pump and poured back into the tank. The attendant enters them (`POST /shifts/:id/tests`, pending); the manager decides once, confirm or cancel (`POST /shifts/:id/tests/:testId/decide`, 409 once decided; also after the closing: `applyTests()` recomputes the readings, the tank stock and `reconcile()`); a manager's own entry is approved at once. Approved litres are not sold: `netLiters()` in `src/routes/shifts.js` subtracts them at closing, and the period reports (`src/checkpoints.js`) per checkpoint period.
- Debts from before the app (`old_debts`: the station's notebook) count in the balance (`balanceSql` in `src/loyalty.js`, used by every balance query) and are settled first by `creditAllocation` (items with `old: true`). The manager adds or removes them on the customer page; the attendant declares one with a payment (`oldDebt`) when the amount is more than the app knows, or keeps the surplus as an advance (negative balance, taken by the next credits). They never suspend a subscriber's credit.
- Cash book (`src/cashbook.js`, `src/routes/cashbook.js`, screen « Caisse »): two balances, cash and mobile money (mobile money reaches the till only through a `retrait_momo` transfer). Entries are derived from closed shifts (cash, mobile money; the cash comes in with the shift's expenses added, and each expense paid from the till goes out on its own line), payments and expenses outside a shift, deliveries paid on the spot and supplier payments; `cash_movements` holds the manual ones, and the latest `opening` count restarts a balance. Tank stock during the open shift (`src/liveStock.js`, version 18): `book_stock` loses the litres sold only at the closing, so a delivery or a dip reads the current index of the tank's nozzles (`meters`, stored in `stock_readings`; `GET /stock/meters` gives the open shift's last index); `withLiveStock()` takes the fuel sold so far (latest index − opening − approved tests) off `book_stock` in `GET /tanks` and the dashboard; a delivery past the capacity is refused (`over_capacity`, `force` to confirm); a dip compares with that live stock and stores `measured + sold`; `lastMeters()` includes these indexes, so the closing cannot go below them. Suppliers have a record (`suppliers`: name, phone, e-mail; admin only, `POST/PUT /suppliers`, a rename follows on `deliveries.supplier` and `supplier_payments.supplier`). Deliveries are `payment` 'cash' (out of the book by `pay_method`), 'shift' (paid with the open shift's money: an expense « Paiement fournisseur » (`SUPPLIER_PAYMENT`) of that shift, supplier required, `deliveries.expense_id`, version 23; changed with the delivery while the shift is open, cancelling the expense leaves the delivery's payment empty; left out of the reports' net result, the fuel cost is already in the margin), 'credit' (a debt to the supplier, settled by `supplier_payments` or by an expense « Paiement fournisseur » (`SUPPLIER_PAYMENT`) whose `beneficiary` is the supplier: `supplierOf()` in `src/cashbook.js` checks and spells it, `supplierExpenses()` counts it in `supplierBalances()`; left out of the net result; `/auth/me` gives the team `settings.supplierNames`, offered as chips by `nameChips()` in `ui.js` under « Payé à » and the delivery's supplier; a delivery's own expense is not counted against the supplier's debt) or 'prepaid' (paid before the app: only the stock). The manager can correct a delivery's payment afterwards (`PUT /deliveries/:id`, journalled), and a nozzle's index while the shift is open as long as no checkpoint has read the meters (the open shift's `start_meter` follows).
- Transport: `settings.shiftTransport` (`shift_transport`, admin, 0 = none) is added by `addShiftTransport()` (`src/transport.js`) as an expense « Transport » of each shift when `openShift()` opens it, and of the open shift when the setting changes; `client_ref` `transport-<shift id>` keeps it once per shift.
- Paid sales are never entered: `POST /shifts/:id/sales` refuses `paid`, and customer requests are on credit (or combos while enabled). The one exception: a payment at the pump for a credit taken in the same open shift goes through `settleInShift()` (`src/sales.js`): the credit becomes kind `paid` (whole, or split with the litres in proportion), a mobile money part is also a `momo_sales` entry, only the surplus is written to `payments`; `sales.settled_ref` (version 25) keeps the form's `clientRef` so a resend does nothing; journalled `credit_paid_in_shift`.
- Meter photos: `withMeterPhoto(field, { product, last, nozzleId, typed })` (`public/js/photo.js`) puts a camera button beside a meter index field, everywhere an index is entered (closing, checkpoints, the manager's meter check in « État du poste », delivery and dip, a meter's index in Réglages; in a `formDialog` or `field()`, the option `meterPhoto: { product, last }`); the photo is reduced on the phone (1280 px JPEG) and sent to `POST /meters/read` (`src/routes/ai.js`), which asks Claude through `src/meterReader.js` (Messages API over `fetch`, structured output `{ readable, digits, index }`, `METER_MODEL` default `claude-sonnet-5-5` at effort low with `fallbacks: "default"` (Haiku misread the station's meters), 25 s timeout, the phone waits 30 s; `checkAgainst()` moves a misplaced decimal point back so the reading follows the last index, else returns `suspect`, shown as a toast; each reading is logged for Render's log); the figure only fills the field. The index is never typed first: while the key is set, the field is locked (`inputmode=none`, typing blocked, a tap opens the camera) until a photo was taken, then `markRead()` opens it for a correction; an unreadable photo or a failed call opens it too (the 422 carries `photoId`: `fail(…, extra)` adds fields to the error reply, `err.data` on the client). `typed: true` keeps a typed field (a meter's index in Réglages, « Corriger la clôture »). An attendant's relief or evening closing needs a kept photo of every meter (`needPhotos()` in `shifts.js`, `code: 'photo_required'`); the closing draft keeps the photo ids (`<name>@photo`). Reports show the figure Claude read beside an index saved differently (`photo_read` / `end_photo_read`, `meterPhotoLink(id, read, index)`). With `nozzleId` (relief, evening closing, closing forms) the photo is kept a week as proof: `src/photoStore.js` writes it next to the database (`photos/`, never in it nor in backups), row in `meter_photos`; the form sends `readings[].photoId` (`input.dataset.photoId`), `linkPhotos()` in `shifts.js` sets `checkpoint_id` / `closing_shift_id`; reports show `meterPhotoLink()` (`nozzles[].photo_id` in `periodReport()`, `readings[].end_photo_id` in the shift detail) opening `GET /meter-photos/:id`; `photos.cleanup()` runs in the mail jobs' tick and deletes files and rows after 7 days. Shown when the key is set (below). The icon is a PNG from pngegg.com drawn through a CSS mask (`.png-icon`).
- Claude (`src/claude.js`: `ask()` over the Messages API with `fetch`, structured output, `fallbacks: "default"`; `imageParam()`; `aiEnabled()` = `ANTHROPIC_API_KEY` set → `settings.ai` from `/auth/me` → `flags.ai`, `photosOn()` in `public/js/photo.js`). Photo routes are in `src/routes/ai.js` (3 MB body limit for them in `app.js`); nothing is saved from a photo, what was read fills a form. Besides meters: `POST /customers/plate/read` (`PHOTO_MODEL`, Sonnet 5.5) reads a plate and finds the customer (main plate, else the last credit with it) for the credit form (field option `photo: { label, onImage }`, `customerSearch().pick`); `POST /customers/notebook/read` (manager, `NOTEBOOK_MODEL`, Opus 5.5, the customers' names given to match) returns lines of the old debts notebook, checked in `notebookDialog()` (`customers.js`), then `POST /customers/notebook/import` creates the missing customers (needs_review) and the `old_debts` (« Cahier »), journalled `notebook_import`. `src/reportComment.js` `periodComment()` (`REPORT_MODEL`, Opus 5.5) writes 3 to 5 observations at the top of the week's and month's report mails from `salesReport()` of the period and the previous one plus the open alerts; `periodReport()` in `mailJobs.js` waits for them only when the key is set (the tests stand in for Claude by replacing `claude.ask`) and sends without them on failure.
- Forms from the attendant's phone send a `clientRef`: sending it again returns the first record (unique `client_ref` on sales, payments, expenses).
- Without network (`public/js/api.js`, `public/sw.js`): the service worker keeps the app's files (network first, the copy when it fails; main.js sends it the files loaded); `api.js` keeps the last answer of a few GETs (`KEEP`: setup, me, shift state, remarks, customers of the forms, pumps) in `localStorage` (`cache:<url>`, per signed-in user, cleared at logout) and returns it when the network fails; `api.post(url, body, { queue: label })` puts an entry in the outbox (`localStorage` `outbox`, per user) and returns `{ queued: true }` (the attendant's credit, payment, mobile money, expense and pump test forms; `queued()` in `attendant.js`). `flush()` sends it in order when the server answers again (`online` event, every 20 s, after any answer); a 4xx drops the entry and reports it (`outbox:sent` → a notice in `main.js`), a network error or 5xx keeps it. The shell's `net-strip` shows « Hors connexion · à jour à HH:MM · N en attente d’envoi » (`net:change`).
- WhatsApp receipt: `receipt(customer, lines, balance)` in `ui.js` builds the `wa.me` link (the customer's number by `whatsappNumber()`, else a contact picked), shown as the « Reçu » action of the `toast(message, type, { action })` after a credit or a payment (attendant and customer record); `POST /shifts/:id/sales` returns the customer's `balance` for it.
- « Demander à l'appli » (`src/assistant.js`, `POST|GET /ask` in `src/routes/ai.js`, manager/admin/owner): Claude (`ASK_MODEL`, Sonnet 5.5, `claude.converse()` with the `sql` tool, system prompt cached: the live tables from `sqlite_master` minus `HIDDEN`, and the station's rules) writes SELECTs run by `runSql()` (SELECT/WITH only, `PRAGMA query_only` while it runs, 200 rows, secrets refused by name and masked in the rows); at most 8 turns. Each question is kept in `ai_questions` (tokens too); `settings.askMonthLimit` (`ask_month_limit`, admin, 50, 0 = off) caps the station's questions per month (`code: 'ask_limit'`); `/auth/me` `settings.ask` → `flags.ask` shows `askCard()` on the dashboard. The tests stand in for Claude by replacing `claude.converse`.
- Journal: `audit(db, req, {...})` in `src/audit.js` writes `audit_log` (category, summary, before/after JSON, reason). Call it for any change a manager should be able to trace; an accepted cancellation keeps the deleted row there.
- Scheduled prices (`products.next_price*`) are applied by `applyScheduledPrices()` (`src/prices.js`) at shift opening and when prices are listed.
- PDF reports are built on `src/pdfReport.js` (`Report`: section, line, table, paragraph, finish) over `src/pdf.js`, readable once printed on A4: nothing is cut with « … », text wraps (titles, notes, labels, cells); `table()` sizes its columns with `layout()` (figures, right-aligned, keep one line at the width they need; short text columns keep one line; long ones share the rest by their `width` hint and wrap), at 9.5 pt, down to 8.5 pt for a table too wide. A column `width` is a hint, not a fixed size: shift, period (with the cash book of the period: both accounts' balances and every movement, from `cashbook()`) and customer statement (`?from&to`, or `?month`; « Partager » in the statement card shares the period shown, `shareUrl` of `statement()` → `sharePdf()` in `ui.js`).
- Cancelling an operation (sale, mobile money entry, payment, expense):
  - the attendant only asks: `POST /shifts/:id/:kind/:itemId/cancel`, which sets `cancel_requested_*`;
  - the manager decides: `DELETE` cancels it, `POST …/keep` keeps it;
  - `reconcile()` recomputes a closed shift after a cancellation;
- The manager's remark on a closed shift (`POST /shifts/:id/remark`) is read by the attendant: an unread remark shows on their home screen (`GET /shifts/remarks/unread`) and is marked read when they open the shift (`comment_seen_at`).
- Customer purchase requests (`src/routes/requests.js`): pending for 30 min. Attendants poll `/requests/pending` (every 4 s on the client); a request becomes a sale only when confirmed.

**Frontend** (`public/`, no framework, native ES modules):
- `public/js/main.js`: hash router, a `NAV` table per role, a persistent app shell, and View Transitions between screens.
- One file per screen in `public/js/views/`; each exports `render*(page, ctx)`.
- `public/js/ui.js` is the shared toolkit:
  - `h(tag, attrs, ...children)` DOM builder;
  - `setContent(el, ...children)`: always use it instead of `replaceChildren`, because it flattens arrays and skips null;
  - `fmt` (fr-FR money/litres/dates; `parseServerDate` handles SQLite UTC timestamps and date-only strings);
  - `formDialog` (iOS-style sheet; field types include `segment`, `checkbox` switch, `select`, `hidden`, `list` datalist), `confirmDialog`, `actionSheet`, `segmented`, `toast`.
- `public/js/api.js` throws errors carrying `.status` and `.code`.
- Design: « Totem de nuit », the station's price totem at night (chosen by the user): black ground, gasoil green and essence red fields, condensed figures, white action slabs, a day mode for full sun (the sun key beside the account, `themeButton()`).
  - Shell: side rail on wide screens; top bar + bottom tab bar (four tabs + Plus) below 1024px; forms open as a right drawer from 834px and as bottom sheets below.
  - Colour and shape: the main action (Confirmer, Enregistrer, Terminer…) is a porcelain slab, ink by day (user's request, 2026-10-06); Annuler / Fermer is the ground itself, outlined (`.btn.cancel`; a destructive cancel stays red); Retour is MTG blue (`.btn.return`, `--mtg-blue`, and the ‹ link above a detail page); every other button and every card header is lit sky, violet or orange, neighbours taking turns (`--sign-*` tokens, `:nth-child(… of …)` in `app.css`). One shape everywhere, the rounded rectangle: no circle, no pill.
  - Signatures: `priceTotem` and `shiftLine` in `ui.js`, count-up in `public/js/motion.js`, the brand film on the sign-in screen.
  - Logo: the MTG monogram of MTG Industrie, redrawn (`public/media/mtg-monogramme.svg`): `brandMark()` in `icons.js` (letters in the text colour, the M's leg and the G's dot in `--mtg-blue`), the phone icons (`public/icons/`), the favicon in `index.html`, and « MTG / Station » in the mail header (`public/media/mail-logo.png`).
  - The tokens and rules are in `DESIGN.md`, the product facts in `PRODUCT.md`, and the direction in `.impeccable/surfaces/`. The Impeccable design skill is installed in `.claude/skills/impeccable`.
- CSS: tokens, components and both themes are in `public/css/app.css`; reuse its classes rather than inline styles. Fuel colours go through `productColor(id)` / `--gasoil`, `--essence`. Inter and Barlow Condensed are self-hosted in `public/fonts/`.
- Brand film: the HyperFrames source is `videos/mtg-totem-sting/`; the rendered WebM/MP4 and poster live in `public/media/`. Re-render and re-encode after changing it.

- The attendant screen is used on a phone with a queue of customers waiting, so keep it to as few taps as possible.

**Mails** (version 22):
- `src/mail.js` sends through Resend's HTTP API with Node's `fetch` (no dependency): `RESEND_API_KEY`, `MAIL_FROM`, `MAIL_REPLY_TO`. Every mail is written to `mail_log` at once (`queued`, or `skipped` without a key: tests and development send nothing) and sent afterwards, one at a time; `outbox` keeps the last 100 in memory (the tests read links from it).
- `src/mailTemplates.js` `renderMail(mail, station)`: one layout like the big senders: the text with no page colour (the mail app's own, light or dark, `color-scheme: light dark`), only the header (the night band edge to edge, square, the logo a link to `APP_URL`, gasoil/essence stripe) and the buttons (ink, porcelain in a dark mail app) are filled; the contact icons (SMS, WhatsApp, call: `public/media/mail-*.png`, PNGs from pngegg.com as the user asked, black, inverted in a dark mail app) built from blocks (`p`, `amount`, `rows`, `list`, `button`, `code`, `note`), with the plain-text version. Tables and inline styles only.
- `src/mailer.js` `createMailer(db, mail)` (`app.locals.mailer`, passed to every route factory as `(db, { mailer })`): who gets what (`MAIL_KINDS`; switched off per account in `mail_prefs`, per customer record in `customer_mail_prefs`), one-time links (`mail_tokens`: reset 1 h, verify 7 days), and the request-driven mails: `sendReset`, `sendVerify`/`confirm`, `passwordChanged`, `noteLogin` (cookie `did`, `known_devices`: « Nouvelle connexion » from a device not seen before), `sendAccess`. The team's address is `users.email` and only receives once confirmed (`email_verified_at`); a customer's is `customers.email` (any mail; « mot de passe oublié » only once confirmed). Links point to `APP_URL`, else the host the app was last reached at. Customer mails carry a signed « stop » link (`settings.mail_secret`, `GET|POST /api/mail/stop`).
- `src/mailJobs.js` `createMailJobs(db, mailer)`: `tick({ now, settle })` every minute (`server.js` calls `start()`; the tests call `tick` themselves): receipts, credit fill-ups and new prices read past a cursor (`mail_cursors`, a minute late), shift reports once counted, new dashboard alerts (`mail_alerts_sent`, filtered by `userAlerts`), the week's and month's reports, statements on the 1st, subscriber reminders, the Sunday backup. Scheduled mails are written in `mail_jobs` before they go; the first tick starts every cursor and list from what exists. The PDFs and alerts come from the routes (`router.shiftPdf`, `periodPdf`, `stationAlerts`, `customerStatement`, gathered in `mailer.services` by `src/app.js`).
- Routes (`src/routes/mail.js`): `POST /auth/forgot` (same answer whatever the login), `GET /auth/reset/:token`, `POST /auth/reset` (ends every session, signs in), `GET /mail/verify` and `/mail/stop` (redirect to `/?mail=…`, shown by `mailNotice()` in `main.js`), `GET|PUT /me/mail` (« Mes mails » in the account menu, every role), `GET /mail/status` (Réglages → Mails, with `mailUsage()` from `src/mail.js`: today and this month against `MAIL_DAY_LIMIT` 100 / `MAIL_MONTH_LIMIT` 3 000, Resend's free plan; from 80 % a `mails_limite` dashboard alert). Screens: `renderForgot` / `renderReset` in `views/auth.js` (`#/mot-de-passe-oublie`, `#/mot-de-passe/<lien>`, handled in `boot()` before the session check).

## Deployment

`src/storage.js` tells on Render whether the database is on the persistent disk (`/api/health` `storage`, a warning in the log otherwise). `render.yaml` is a Render blueprint (`TZ=Africa/Lubumbashi`, `DB_FILE` on a persistent disk, health check `/api/health`). The SQLite file is the whole state; back it up with Réglages → Données (`GET /api/backup`, `VACUUM INTO`), never by copying `station.db` alone (WAL).
